# Private instance onboarding

The instance owner approves exact Gmail addresses.
Every person receives a distinct internal user ID.
Never map a friend to the owner's existing ID or copy the owner's profile into their account.

## Production identity setup

1. Register the chosen domain and add it to the existing Vercel project.
2. Add the DNS records Vercel supplies, verify HTTPS, and redirect the previous app domain to the canonical domain.
3. Create the Clerk production instance for that domain and complete Clerk's DNS verification.
4. Enable restricted sign-up and add only the approved Gmail addresses.
5. Configure production Google sign-in credentials in Clerk with identity scopes only.
6. Disable unused sign-in methods, including GitHub and password sign-up if Google-only access is intended.
7. Set the production Clerk publishable and secret keys in Vercel's Production environment, then deploy.
8. Update `TRACKER_USER_MAP` with the exact verified primary Gmail address and its unique internal ID.

The app checks the verified primary address on every signed-in operation.
Script API keys also require their internal user to remain in the approval map.
Clerk's allowlist prevents unwanted registrations; the server approval map controls access to instance data.
Do not use a wildcard Gmail-domain allowlist.
Clerk production user IDs differ from development IDs, so verify the existing owner's email mapping before switching keys.

## Enroll one friend

1. Take and verify a recoverable backup before the first multi-user rollout.
2. Add one approved Gmail address to Clerk and the server map, with a new internal ID such as `friend_01`.
3. Have the friend sign in and confirm that their dashboard, profile, applications, connections, and settings are empty.
4. Have them create or import their own resume profile and review the imported facts before saving.
5. Explain the shared model allowance and how an optional personal provider key changes billing.
6. Offer Gmail inbox synchronization separately from sign-in.
7. Verify that their first saved profile, application, and resume remain invisible from a second test account, including direct API and file URLs.
8. Issue an individual script key only if they need scripts, store its hash in `TRACKER_API_KEYS`, and deliver the raw key privately.
9. Complete watcher enrollment only after the watcher policy below has been decided and implemented.

Approving login alone does not enroll the current YAML-driven watcher.
Do not promise job discovery or backfill until that separate step is complete.

## Watcher decisions awaiting the owner

- Keep one shared source fetch and then filter per user, or run independent fetches.
- Enroll approved users automatically using app preferences, or continue maintaining a YAML file for each user.
- Show existing matching jobs on first use without emailing the backlog, show only new jobs, or send an initial digest too.
- Use a shared project sender, require personal senders, or begin without digests.
- Define which filters and digest schedules friends can change.
- Define one disable operation covering web access, API keys, discovery, digests, Gmail sync, and queued paid work.
- Make per-user failures visible and retry only the failed user's delivery without duplicating successful digests.

Do not clear shared watcher state to onboard a new user.
That would make old jobs appear new for everyone.

## Gmail OAuth setup

App sign-in and inbox synchronization are separate connections.
Keep the Gmail client separate from Clerk's identity client so inbox permissions remain optional.

1. Use a Google Cloud project controlled by the instance owner, enable Gmail API, and configure OAuth branding, audience, contact email, and authorized domains.
2. Use the selected app domain for homepage and privacy-policy URLs.
3. Register the exact callback generated by the app's current Gmail flow; copy it from the configuration instead of guessing a path.
4. Configure the Gmail client ID and secret in the backend, together with the Pub/Sub topic and push authentication settings documented in the Gmail setup guide.
5. Request only the scopes the implementation uses, including Gmail read-only access for synchronization.
6. Test connecting, syncing a synthetic application email, disconnecting, and reconnecting with an approved test user.
7. Check Google Cloud's publishing status before inviting friends.

External apps in Testing generally receive seven-day refresh tokens when Gmail scopes are requested.
Moving to In production does not make app sign-up public.
Google's personal-use verification exception may apply to a small set of personally known users, but unverified warnings and applicable user caps remain.
Confirm eligibility against Google's current guidance before relying on it.
Gmail read-only is a restricted scope; broader use can require verification and additional assessment.

Disconnect Gmail removes the local token and stops future synchronization writes.
Already completed tracker history stays.
An API request already sent to Google can finish, but its result cannot update a disconnected account.
The user can additionally revoke the grant in their Google account's connections page.

## Remove access

Until a unified disable control is implemented, complete every applicable step:

1. Remove the Gmail address from Clerk's allowlist and revoke its active sessions.
2. Remove its entry from `TRACKER_USER_MAP` and redeploy the web app.
3. Remove any script key entries for the internal user.
4. Disconnect the user's Gmail account while administrator access is available.
5. Remove or disable its watcher enrollment and pending deliveries after the watcher policy is implemented.
6. Retain or delete personal data according to the agreed retention policy, including retained backups.

Removing login access alone does not stop the current independent watcher or mailbox jobs.

## Rollout acceptance

The first invite is ready only after production identity is verified, the backup restore drill passes, cross-user reads and writes fail, and watcher enrollment and revocation have a tested procedure.
Keep the initial rollout to one friend and verify a full discovery and digest cycle before adding the next.
